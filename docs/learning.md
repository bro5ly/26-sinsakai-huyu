# 学習メモ

開発者が、このシステムの仕組みを実際のコードで学んだ記録(`docs/backlog.md`のL2)。理解を確かめた日付ごとに足す。

## 1. Webのセッション認証(2026-11-02)

### 流れ(開発者のまとめ。Claudeが確かめた)
**ログインのとき**
1. サーバーが、推測できない乱数の番号(セッショントークン)を作る
2. そのハッシュ(SHA-256)を、`user_id`・種類(`WEB`)・期限(7日)と一緒に、DBの`session`の表に1行で保存する
3. トークン本体は、ブラウザのCookie`session`に入れる(本文には入れない)

**認証が要るリクエストのたび**
1. ブラウザが、Cookieのトークンを自動で付けて送る(画面のコードはトークンを触らない)
2. ミドルウェア(`createAuthMiddleware`)が、トークンをハッシュにする
3. そのハッシュで、`session`の表の`token_hash`を一意の索引で検索する
4. 見つかった行で判断する(行がある・期限内・種類が合う・無効な人でない)。通れば、その行の`user_id`が本人

```ts
// back/src/middleware/auth.middleware.ts
checkSession(await sessions.findSessionByTokenHash(hashToken(token)), "WEB", new Date());
//                                                 └ハッシュにする   └Cookieのトークン
//                       └ token_hash の索引で1行を引く(無ければ null)
//          └ 期限・種類・無効な人を確かめる
```

### 分かったこと
- **Cookieの中身は、意味の無い乱数だけ**。userIdも期限も入っていない。デコードしても乱数のバイトが出るだけ。誰かの情報はDBの行にある(トークンは、その行を探すための合言葉)
- **本人を特定するのは「デコード」ではなく「探す」**。ハッシュは一方向で、トークンからハッシュは作れるが、ハッシュからトークンには戻せない。だからサーバーは、届いたトークンから毎回ハッシュを作って、同じ値の行を探す
- **ハッシュにする処理は鍵ではない**。SHA-256は公開された計算で、誰でも同じ計算ができる。秘密(鍵)はブラウザのトークンのほう。たとえると、トークンが鍵、`token_hash`が鍵穴の形の記録、ハッシュにする処理が「鍵穴に合うかを見る仕組み」
- **ブラウザにハッシュを載せない理由**: 載せると、Cookieの値とDBの値が同じになり、DBの値そのものが合言葉になる。DBが漏れたら全員になりすませる。今の形なら、漏れるのはハッシュだけで、それを送ってもサーバーがさらにハッシュにするので通らない(パスワードを画面でハッシュにして送らないのと同じ。pass-the-hash)
- **SHA-256で探せて、bcryptで探せない理由**: SHA-256は同じ値からいつも同じハッシュになるので、`WHERE token_hash = ...`で探せる。bcryptは毎回ソルトを混ぜて違う値になるので探せない。トークンは256ビットの乱数で推測できないので、速いSHA-256で足りる。パスワードは人が決める短い値なので、遅いbcryptにする
- **ログインのたびに行を増やす**(1つの行を書き換えない)。ログインのたびに番号を作り直すと、前もって決めた番号をつかませる攻撃(セッション固定)を防げる。行が端末ごとにあるので、パソコンでログアウトしてもスマホは切れない。期限の切れた行を片付ける処理はまだ無い(残タスクの「掃除」)
- **主キーの`id`とトークンは別物**。主キーはDBの中で行を区別する値で、ブラウザには渡さない。連番や推測できる値は合言葉に使わない
- **毎回DBを引く**。ログアウト(行を消す)・無効にした人・管理者でなくした人が、次のリクエストからすぐ止まる。1回の手間は索引で1行を引くだけ
- **Cookieの設定はブラウザへの指示**: `HttpOnly`(JSから読ませない。XSSで盗まれにくい)、`SameSite=Strict`(別のサイトからのリクエストには付けない。CSRFの対策)、本番は`Secure`、`Max-Age`は7日。指示はブラウザが覚えるだけで、送り返されるのは`Cookie: session=<トークン>`の1行だけ。本当の期限はDBの`expires_at`で決める
- **画面の`AuthContext`は守りではない**。開いたときに`/api/me`を1回呼ぶのは、画面の出し分け(ログインの画面に送るか)のため。データを守るのは、毎回のAPIの確かめ

### JWTとの違い
| | 今の方式(トークン + DB) | JWT |
|---|---|---|
| Cookieの中 | 意味の無い乱数 | userIdなどの中身 + 署名(デコードすれば誰でも読める) |
| 本人の特定 | ハッシュにしてDBで探す | 署名を確かめて、中身を読む(DBは引かない) |
| すぐに取り消せるか | できる(行を消す) | 難しい(期限まで通る) |

このプロジェクトは前はJWTだったが、すぐに取り消せるように今の方式にした(2026-10-28。`docs/auth.md`の2章)。
