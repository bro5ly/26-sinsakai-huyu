# 認証の作り直し 要件と方針

タブレット(公共の場に置く)と、学籍番号・カードの番号の扱いを見直す。全体の要件は`docs/spec.md`、今の仕組みは`docs/architecture.md`の「認証とトークン」。

2026-10-23に、今のコードとAPIを確かめて書いた。**要確認A-Q1〜A-Q8は、2026-10-23に叩き台どおりに決定した。**

## 1. 目的と背景

今のタブレットの認証は、次の状態になっている(確かめた結果)。

- カードの番号(シリアル番号)だけで本人確認する。カードの番号はバーコードで誰でも読め、写真でも写せる。ダッシュボードにも同じバーコードが出る
- タブレットの端末を確かめていない。`/api/tablet/*`はどこからでも呼べるので、カードの番号が分かれば学校の外から他人の名前で借りた記録を作れる
- カード認証の応答に名前・学籍番号・学年・専攻・借りている物が入る。回数の制限もないので、番号を順に試せば個人情報を集められる
- タブレットのトークンは3分のJWTで、取り消せない。画面は無操作1分で戻り、完了画面から「続けて操作」できる。立ち去ると次の人が前の人の名前で借りられる
- Webのアクセストークンでタブレットの貸し出しが通る(鍵が同じで、`role`を見ていない)
- 無効にした人(`is_active = false`)も認証できる
- ログイン・認証コードに失敗の回数の制限がない。学籍番号が名簿にあるか・登録済みかが、応答の違いで分かる

成功の目安: **カードの写しだけでは借りられない。学校の外からは借りられない。立ち去った人の名前で次の人が借りられない。**

## 2. JWTとサーバーのセッションの使い分け

| | JWT(署名付きトークン) | サーバーのセッション(推測できない乱数の番号をDBに持つ) |
|---|---|---|
| 確かめ方 | 署名と期限を見るだけ。DBを見なくてよい | 毎回DBで探す |
| 期限前に取り消す | できない(取り消すにはDBに黒リストが要り、JWTの良さが消える) | 行を消せばすぐ無効 |
| 向いているもの | 短命で、取り消せなくても困らないもの。複数のサービスで同じトークンを確かめたいとき | 取り消しが要るもの。1回使ったら終わりにしたいもの |

方針(2026-10-28に見直した。`docs/backlog.md` 0.8 のA8-3〜A8-5):
- **タブレットの本人確認のセッションは、サーバーのセッションにする**(JWTをやめる)。1回の操作で終わらせたい・立ち去ったらすぐ無効にしたい・端末と結び付けたいので、取り消せることが一番大事
- **Webのログインも、サーバーのセッションにする**(A8-3。2026-10-23の「WebはJWTのままでよい」を改めた)。JWTのアクセストークンとリフレッシュトークンをやめ、セッションの番号をHttpOnly Cookieで持たせる。理由: 無効な人を通さない確認(R-A14)で毎回DBを読むのでJWTの良さが消える。APIは1台・DBは1つ。管理者がWebのセッションも消せる。トークンをJSから読めるCookieに置かなくて済む(XSSで盗まれない)。方式を1つにすれば、トークンの取り違え(ずれ3)が起きない。代わりにCSRFの対策が要る
- **タブレットの端末の登録も、サーバーのセッションと同じ仕組み**(管理者が取り消せる)。ただし表は人のセッションと分ける(A8-5)
- **Webのセッションの長さ**: 作ってから7日で必ず切れる。無操作の期限は持たない(A8-6)。名簿から消えた人はログインのときだけ確かめ、無効な人(`is_active`)はリクエストのたびに確かめる(A8-10)
- **CSRF**: セッションのCookieは`SameSite=Strict`・HttpOnly(本番はSecureも)。書き換えのリクエストは、`Origin`が画面のURLと同じでなければ403 `FORBIDDEN_ORIGIN`で断る(A8-7・A8-11)
- **登録用トークン(15分)も、DBに持つ番号にし、1回使ったら消す**(A8-8)。2026-10-29にタブレットのセッションもでき、JWTは使わなくなった(`jsonwebtoken`も外した)
- 作り: `crypto.randomBytes(32)`で番号を作り、DBにはハッシュ(SHA-256)だけを持つ。番号を作る・確かめる関数は、Web・タブレット・端末で共通にする。ライブラリ(`express-session`・Better Auth・Auth.js)は使わない(A8-4。名簿を写さない決まりと、カード + PINの流れに合わせるため)

## 3. 学籍番号とカードの番号の区別

| | 学籍番号 | カードの番号(シリアル番号) | 利用者のID(`user.id`) |
|---|---|---|---|
| 何か | **誰か**を表す名前。学校が決め、変わらない | **持ち物**(カード)の番号。カードを無くすと変わる | このシステムの中だけの番号(UUID) |
| 秘密か | 秘密ではない(名簿・名札・提出物に書く) | **半分秘密**として扱う(見せない・記録に出さない) | 秘密ではないが、画面に出さない |
| 使い道 | Webのログインの「ID」、名簿を引く鍵 | タブレットで「カードを持っている」ことを示す | テーブルどうしのつながり、トークンの`sub` |
| 単独で本人確認に使うか | **使わない**(パスワードと組にする) | **使わない**(PINと組にする。A-Q3) | 使わない |
| 画面・APIの応答に出すか | 本人のダッシュボードだけ | **出さない**(ダッシュボードのバーコードもやめる。A-Q6) | 出さない |
| ログに出すか | 出さない | 出さない | 出してよい(調べるとき用) |
| 持ち主 | 名簿(学校) | 名簿(学校)。カードの交換は名簿の更新で反映する | このシステム |

## 4. 修正案

### 4.1 タブレットの端末を登録する(タブレットのページ自体の認証)

2026-10-29に作った(0.8のd。決め事はD1〜D6、`docs/backlog.md`)。登録のAPIは本文で管理者を確かめ、Webのセッションは作らない(D2)。Cookie`device`は400日で、使うたびに付け直す(D3)。

- **R-A1** 管理者がタブレットで管理者のIDとパスワードでログインし「この端末を登録」すると、システムは端末用の番号を発行し、HttpOnly Cookieでその端末に持たせる。DBには端末の名前・ハッシュ・登録した人・最後に使った日時を持つ
- **R-A2** `/api/tablet/*`は、登録された端末の番号が無ければ、どれも401で断る
- **R-A3** 管理者は、端末の登録を取り消せる(盗まれた・使わなくなったとき)。取り消した端末は次の呼び出しから断る
- **R-A4** (任意)学校のネットワークからだけ受け付ける設定を持てる(A-Q2)

### 4.2 カードの番号 + PIN(サイト内で登録する暗証番号)

PINの登録は2026-10-28(0.8のc)、タブレットでの確かめ・ロック・セッションは2026-10-29(0.8のe1)に作った。5回目の間違いの応答から`PIN_LOCKED`にする(E5)。

- **R-A5** 利用者は、Webでログインして、タブレット用のPIN(数字4桁)を登録・変更できる。登録・変更のときはパスワードを入れ直させる(P1)。同じ数字の並び・連続した数字は断る(P2)。PINはbcryptのハッシュだけを保存する。ただし4桁は1万通りしかなく、DBが漏れればハッシュから総当たりで分かる。守りはタブレットでのロック(R-A7)と端末の登録(R-A1〜A3)にある(2026-10-28)
- **R-A6** タブレットで借りるときは、カードの番号を読んだあとにPINを入力する。PINを登録していない人も、カードとPINが合うまでは「カードかPINが違います」で断り、借りさせない(A-Q3。PINの登録はダッシュボードで案内する。R-29)
- **R-A7** もしPINを続けて5回間違えたら、そのカードのタブレットでの認証を止め、Webでログインし直してPINを再設定するまで止めておく
- **返却はカード・PINを要らない**(返却は本人でなくてよいと決めた。Q3)。登録された端末であれば、物品のバーコードを読むだけで返却できる(A-Q4)

### 4.3 タブレットのセッションの期限

- **R-A8** カード + PINが通ったとき、システムはサーバーのセッション(上の2章の形)を作る。セッションは**その端末でだけ**使える
- **R-A9** セッションは、最後にタブレットからサーバーへ送ってから30秒で切れる。作ってから3分を超えたら、操作中でも切れる(A-Q5)。画面も同じ「最後にサーバーへ送って通ったときから30秒」で最初の画面に戻す。「借りる」を選ぶなど、サーバーに送らない操作では延ばさない(画面だけ延ばすと、操作中なのにサーバーでは時間切れになるため。2026-10-30 A1)
- **R-A10** 利用者が「終わる」を押したとき、または完了画面を出してから10秒たったとき、システムはセッションをすぐ無効にする。完了画面から10秒以内に「次の操作」を選べば、同じセッションで続けられる(何冊か続けて借りる人のため。続けて借りる人は少ないので、10秒で必ず終える。2026-10-30 B3、開発者が決めた)
- **R-A11** セッションが切れたとき、タブレットは最初の画面に戻り「もう一度カードを読んでください」と出す(APIはRFC 9457の形で401 `SESSION_EXPIRED`を返す)

### 4.4 カード認証の応答から個人情報を外す

- **R-A12** カードの番号を送った時点の応答は「PINを入力してください」だけにする。カードが有効かどうかも、PINが通るまで分からないようにする(番号を順に試しても何も分からない)。**ただし、PINがロックされたカードは、PINを確かめる前に「PINがロックされています」と出す**(判断表T4。分かるのはロックされたカードだけで、本人が「Webで決め直せばいい」とすぐ分かるほうが大事なため。2026-10-30 B2、E5)
- **R-A13** PINが通ったあとの応答は、画面に出すものだけにする: 表示用の名前だけ。**借りている物・学籍番号・学年・専攻・カードの番号・利用者のIDは返さない**(借りている物は、公共のタブレットで後ろに並ぶ人にも見えるので出さない。返すときは物を持ってくるので要らず、ダッシュボードで見られる。2026-10-30 A2。前は借りている物の名前・期限・延滞を出していた)

### 4.5 無効な人を通さない

- **R-A14** もし利用者が無効(`is_active = false`)・名簿にいない(Q13)なら、システムはWebのログイン・Webのセッション・タブレットの認証を、どれも断る(Webのセッションでは`is_active`だけを毎回見て、名簿はログインのときに見る。A8-10)。理由はPINが通る前には言わない
- **R-A15** 貸し出しが止められている人(`can_borrow = false`・停止期間中・延滞中)は、認証は通るが、借りる操作は断る(判断表C4〜C6)

### 4.6 総当たりと列挙の対策

| 対象 | 対策(叩き台) |
|---|---|
| Webのログイン | 学籍番号ごとに続けて5回失敗したら15分止める。止めている間と5回目の応答は429 `RATE_LIMITED`(2026-10-29 F1。端末の登録の管理者のパスワードも同じに数える)。加えて、接続元(IP)ごとに失敗を15分で100回まで(接続元ごとの分は2026-10-24に20回で入れ、学籍番号ごとの分を入れた2026-10-29に100回にした。学校の回線では全員が同じ接続元に見えるので、成功したログインは数えない(K9-B)。`docs/backlog.md` 0.8 K9-C・F2) |
| 認証コード(登録) | 1つのコードで5回間違えたら、そのコードを無効にする(R-8)。再送は学籍番号ごとに1分に1回、1時間に5回まで(名簿にいない番号も同じに数える。F5)。コードは暗号用の乱数で作り、ハッシュで保存し、比べるときは時間の差が出ない比べ方(`crypto.timingSafeEqual`)を使う(2026-10-29) |
| PIN(タブレット) | カードごとに5回でロック(R-A7)。端末ごとに1分で失敗20回まで(2026-10-29。成功は数えない) |
| カード認証 | PINと同じ1回の本人確認(`POST /api/tablet/sessions`)なので、上の端末ごとの回数に入る(端末の登録で、そもそも外からは呼べない) |
| 列挙(学籍番号があるか・登録済みか) | 登録の申請は、あってもなくても「登録できる学籍番号なら、メールを送りました」と同じ応答にする。ログインの失敗は「学籍番号かパスワードが違います」だけにする(Q2・R-16) |

回数の数え方: 接続元・端末ごとの制限と認証コードの再送は`express-rate-limit`(メモリ。1台のAPIなら足りる。`lib/rate-limit.ts`)、学籍番号・カードごとの失敗の回数はDBの列(`user`の`login_failed_attempts`・`login_locked_until`・`pin_failed_attempts`・`pin_locked_at`、`verification_codes`の`attempts`)に持つ(`features/auth/attempt.check.ts`・`features/tablet-sessions/tablet-session.check.ts`)。

### 4.7 トークンの用途を分ける(ずれ2・3)

2026-10-28にWebもサーバーのセッションにした(A8-3)ので、登録用トークンもDBの番号にする(A8-8)ので、R-A16・A17は、タブレットのセッションを作り直す(0.8のe)までの間だけのタブレット用のJWTにしか当てはまらなかった。2026-10-29にJWTを使わなくなったので、今は当てはまる所が無い。

- **R-A16** JWTは用途ごとに別の鍵で署名する。鍵を使い回さない
- **R-A17** すべてのJWTに用途の印(`typ`)を入れ、確かめるときに印も確かめる。署名の方式は`HS256`に固定して確かめる(`algorithms: ["HS256"]`)
- **R-A18** Webもタブレットもサーバーのセッションにし、セッションの種類(Web・タブレット)をDBに持って確かめる。Webのセッションでタブレットの操作は通らず、その逆も通らない
- **R-A19** ログアウトしたとき、DBのセッションも消す(R-15、ずれ8)

## 7. 変える場所(要件が決まってから)

- DB: `tablet_device`(端末)、セッションの表(Webとタブレットの本人確認。種類の列で分ける。`refresh_tokens`は無くす。A8-3)、`user`に`pin_hash`・`pin_failed_attempts`・`pin_locked_at`(P4)・`login_failed_attempts`・`login_locked_until`、`verification_codes`に`attempts`と用途(登録・パスワードの再設定。`docs/spec.md` R-36)
- API: `/api/tablet/*`の作り直し(端末の確認 → カード → PIN → セッション)、`/api/me/pin`(PINの登録)、`/api/admin/tablets`(端末の登録・取り消し)
- 画面: タブレットにPINの入力と端末の登録画面、ダッシュボードにPINの設定(使い捨てのバーコードは作らない。G0)
- 環境変数: `JWT_REGISTRATION_SECRET`は足さない(A8-8)。`JWT_REFRESH_SECRET`(2026-10-28)と`JWT_ACCESS_SECRET`(2026-10-29)は消した
- 画面: `AuthContext`はトークンを持たず、「確かめ中・ログインしている・していない」の3つの状態と本人の`Me`だけを持つ(A8-4)
