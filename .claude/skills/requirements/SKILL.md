# 要件定義の書き方

開発者の希望を、作る人が迷わず、テストで確かめられる形に書き起こす。出来上がりは`docs/<機能名>.md`(全体の要件は`docs/spec.md`)。

auto-pass(同じ開発者の別のプロジェクト)の`.claude/skills/requirements`を元に、観点リストをこのプロジェクト向けに書き換えた。

## 原則

- **何を満たすかを書き、どう作るかは書かない。** テーブル名・関数名は「変える場所」の節にだけ書く(作り方は設計の仕事)
- **1文に要件1つ。** 確かめられる形にする(「速く」ではなく「1秒以内に」)
- **やらないことを書く。** 範囲の外を明記すると、後から膨らまない
- **決まっていないことは隠さない。** 「要確認」に番号を振り、Claudeの叩き台の答えを添える。開発者が選ぶだけで済むようにする。決まったら「決定(日付)」と書く
- 画面の文言・利用者の言葉で書く。専門用語は「用語」の節で1回だけ定義する
- 今のコードと違うところは「現状とのずれ」に番号を振って書く(`docs/spec.md`の10章)

## 型

1. **目的と背景**: なぜ作るか。何が良くなれば成功か(数字で書けるなら数字で)
2. **範囲**: やること / あとでやること / やらないこと
3. **利用者と流れ**: 誰が(学生・教職員・管理者・タブレット)、どの順で何をするか。「〜として、〜したい。〜のために」(ユーザーストーリー)を数本
4. **用語**: この機能で使う言葉の定義
5. **機能要件**: 番号付き(`R-1`…)。EARSの型で書く。状態(✅ / △ / —)を添える
6. **判断表**: 条件で結果が変わるところは表にする(**表は開発者が先に書く**か、Claudeの叩き台を開発者が直す)
7. **非機能要件**: 下の観点リストで1つずつ点検する。当てはまらない観点も「なし」と書く
8. **受け入れ基準**: Given/When/Then。seedの値(`back/prisma/seed.ts`)で書く。正常だけでなく、境界と異常も
9. **要確認**: 番号・内容・叩き台の表
10. **変える場所**: 要件が固まってから。DB・API・画面・名簿の窓口・運用のどこを触るか

## EARS(要件の文の型)

Rolls-Royceで生まれた、自然な文のまま曖昧さを減らす型。条件の種類で5つに分ける。

| 種類 | 型 | 例 |
|---|---|---|
| いつも | システムは〜する | ダッシュボードは、借りている物と返却期限を表示する |
| 出来事 | 〜したとき、システムは〜する | 返却のバーコードが読まれたとき、その貸し出しに返却日時を入れる |
| 状態 | 〜の間、システムは〜する | タブレット用セッションがある間、利用者はバーコードを読ませて借りられる |
| 任意の機能 | 〜がある場合、システムは〜する | 利用者が管理者の場合、物品の追加と編集の画面を出す |
| 望まない場面 | もし〜なら、システムは〜する | もし延滞中の物があるなら、新しい貸し出しを断る |

## 非機能要件の観点リスト(このプロジェクト用)

- **名簿**: 学校の名簿(本番は学校のDBかAPI)を、名簿の窓口(`Roster`)を通してだけ読むか。名簿の項目をこのシステムのDBに写していないか。名簿が止まったとき・名簿から消えた人はどうなるか(`docs/spec.md`のQ12・Q13)
- **カードの読み方**: 生徒カードのICチップは将来付く想定。今はバーコードか手入力。読み方に依存しない形(カードの番号を受け取るだけ)になっているか
- **同時操作**: 2台のタブレットで同じ物を同時に扱っても、記録が食い違わないか(DBの制約で守れるか)
- **同じ事実を2か所に持たない**: 他の列から分かるものを列にしていないか(貸出中・延滞は`returned_at`と`due_date`から決まる)
- **権限**: ログインなしで呼べるか、利用者本人だけか、管理者(`role = ADMIN`)だけか。Webのトークンとタブレット用のトークンを取り違えないか
- **個人情報**: 何を新しく持つか、ログに出していないか、他の人に見えるか、卒業したら消えるか
- **時刻**: 期限の境目はどちらに含むか(ちょうどの時刻)。日本時間で何時か
- **画面とAPIの形**: 応答は`{ success: true, ...data }` / `{ message, code }`のままか。画面の型(`front/src/types/`)も直すか
- **運用**: seedの値で受け入れ基準を確かめられるか。管理者が何をいつするか

## 判断表とテストの例の表の書き方

**2種類の表を使い分ける**
- **決まりの表**(判断表): 条件の組み合わせと結果。条件が結果に関係ないところは「—」でまとめる(ISTQBの判断表テストの手順: 条件と動作を挙げる → 組み合わせを並べる → 関係ない条件をまとめる → ありえない組み合わせを消す → 残った1列が1テスト)。例: `docs/spec.md`の6章(貸し出せるか、C1〜C8)
- **例の表**(テストの元): 具体的な値で書いた場面。テストを書くときはこちらを使う。**1行=テスト1件**

**例の表の決まり**
- **前提(どの行も同じ条件)は、表の上に1回だけ書く**。1行でも変える条件は、前提ではなく列にする(前提に書いたままだと、その行が何を変えたのか読み取れない)
- **表は「正常系」「異常系」「境界値」で分ける**。それ以上は分けない
- **列は、どの表も同じにする**(すべての条件と、結果)
- 値は**具体的で、ありそうなもの**にする(seedの値を使う)。日時はミリ秒まで書く(境目のため)
- **1行で変える条件は1つだけ**にし、変えたセルを太字にする
- 結果には、**断る理由**と、**そのあとの状態**まで書く
- 境界値は、**ちょうどの値と、その1つ隣**を組で入れる(同値分割: 同じ結果になる値の仲間からは代表を1つ)
- 全部の組み合わせは並べない。増やすときは、1行足すだけで済むようにする
- テストの名前は「表の番号 + 基準から変えたところ + 結果」(例: `C6 延滞中の物があるなら、断る(overdue)`)。まだ書かない行は`it.todo`で並べる
- テストのファイルでも、関数ごとの`describe`の中を「正常系」「異常系」「境界値」の`describe`で分ける(例の表の分け方と同じ。当てはまるものが無い区分は書かない)

## 受け入れ基準

- `前提(Given)/操作(When)/結果(Then)`。1つの基準で確かめることは1つ
- 正常・境界・異常を入れる
- 作り方ではなく結果を書く。そのまま`curl`やテストの場面にできる粒度にする
